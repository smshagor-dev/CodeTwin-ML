# Go security planner with SQLite persistence

CodeTwin has an optional Go process for proposing a **bounded passive** review
task graph. The desktop and authorization supervisor remain Rust/Tauri. All
approved review plans, steps, handoffs, and findings are persisted by Rust in
the existing `codetwin.sqlite3` database (SQLite WAL). No PostgreSQL,
pgvector, Go SQLite driver, Docker service or network server is required for
this bridge.

## Build and use

From `services/security-engine`:

```bash
go test ./...
go build -trimpath -o codetwin-security .
```

On Windows use `go build -trimpath -o codetwin-security.exe .`.
Tauri's `beforeBuildCommand` and `beforeDevCommand` now run
`npm run build:go-sidecar`. This compiles the Go binary for the Rust target
triple into `apps/desktop/src-tauri/binaries/`, and `bundle.externalBin`
includes it in desktop packages. Developers building from source need Go 1.23+,
Rust and Node. For cross-compilation, set `TAURI_ENV_TARGET_TRIPLE` or
`CARGO_BUILD_TARGET` explicitly. Universal macOS packaging is not supported
by this single-target builder.

At runtime, Rust first locates the installed executable next to the
desktop binary. For debug/development builds, it also checks the
target-triple-suffixed companion generated by `npm run build:go-sidecar` in
`apps/desktop/src-tauri/binaries/`. Release builds do not search developer
source paths. `CODETWIN_GO_SECURITY_BIN` remains an explicit override
requiring an absolute file path. A two-second `--health` handshake checks
protocol identity before accepting a plan; no PostgreSQL daemon is started.

Use **Agents → Propose with local Go** after indexing a project. For an
existing review, **Inspect dependency-ready Go schedule** checks its current
SQLite-backed state. This preview does not dispatch tools. Inspect the
proposed DAG, choose **Use this reviewed task plan**, then create and separately
approve/run the existing Rust review.

## Automated Flow → Task → Subtask → Action

From **Agents**, first prepare a normal indexed project review (optionally
using the Go planner or refined task proposal). Select that planned review and
choose **Prepare automated flow**. Inspect the source/specialist tasks and their
dependencies, then choose **Approve and run complete flow**. That single explicit
approval atomically approves the reviewed Rust plan. The flow then executes all
registered, dependency-ready subtasks automatically, calling the Go scheduler
and the Rust dependency validator before each specialist.

The hierarchy is persisted without duplicating mutable state: migration 0044
binds a flow to one original SQLite review. Each Task groups the existing
delegated Subtasks, whose individual Actions are durable receipts from migration
0043. A read-only flow query displays exact current progress, evidence statuses
and action receipts. Cancellation, failure and interruption stop the supervised
chain without automatic retry after a crash. This is **single-approved passive
review automation**, not permission to target arbitrary networks or run exploits.
Full PentAGI multi-flow dynamic autonomous orchestration is not yet ported.

## Bounded multi-flow queue (SQLite only)

Every flow must be prepared and explicitly approved **individually**. From
Agents choose **Queue approved flow**, then **Run approved flow queue** to
process up to eight previously approved passive security flows in FIFO order.
This is a foreground batch run, not a daemon or hidden background process.
The Rust supervisor verifies every Go scheduling decision and retains its
existing global assessment reservation, cancellation controls, evidence
handoffs and SQLite action receipts. A failed/interrupted review stops the
batch, leaving later queued flows unexecuted.

SQLite migration 0046 records the queue's ordering, terminal status and
timestamps without duplicating evidence. The desktop startup recovery marks
a queue item interrupted if its runner was stopped; it does not automatically
re-execute that item. Cancelled parent reviews are removed from the pending
queue before a claim. If cancellation happens after a claim, the queue receipt
is **cancelled**, not failed; completed, failed and cancelled receipts must
match their reviewed SQLite parent state. The native review claim atomically
rejects a still-waiting queued flow, preventing the single-run entrypoint from
bypassing FIFO order. Queue entries cannot add roles, targets or tools, and
no model-generated proposal grants review approval.

### Live queue progress

The Agents queue updates every 3.5 seconds while the page is mounted and
displays a native progress indicator with **completed / total specialists** and
every currently running role (up to two concurrent specialists), ordered by
its approved position. The legacy first-active-role field remains available
for compatibility. Rust derives all these fields by reading the
existing `native_agent_steps` table and the parent `native_agent_runs` status;
no percentages are guessed, no additional migrations or background services
are needed, and completed count is not confused with attempted count. Terminal
failure, cancellation and interruption retain their original queue receipt and
the last completed specialist count. When a specialist has failed, been
interrupted, or been cancelled, the queue also shows its persisted display
role and status (never scanner output or secrets). Tests compare the current
role to the persisted display label, not the lower-case tool identifier.
All reads are local to SQLite, without sending source data or findings to Go.

### Atomic review finalization

After the native tools finish, Rust now takes the SQLite write lock
**before** deciding whether the parent run was cancelled, failed or completed.
A cancellation committed by another desktop connection takes precedence over
the apparent tool outcome. The supervisor checks the signed handoff chain and
delegation graph while the tentative completed status is **uncommitted**; any
failed verification changes it to failed within the same transaction.
Pending/running child steps, receipts and delegations are retired before this
single final commit. No other connection can observe a completed review that
has not passed evidence verification. File-backed tests verify cross-connection
cancellation, invalid handoff downgrade and durable terminal status.

### Completed specialist receipt consistency

A security review may be published as `completed` only after the supervisor
matches **one completed action receipt per approved specialist** against its
persisted position, registered tool, completed step state, finished timestamp
and SHA-256 digest of the exact saved result bytes. Missing, extra, malformed,
failed or digest-mismatched receipts downgrade the parent to `failed` inside
the same finalization transaction; an unverified completed status is never
visible to another SQLite connection. File-backed regression tests cover
unchanged evidence, modified result bytes, modified digests, removed receipts
and mismatched statuses. The desktop review verification and exported review
report re-run the same consistency audit on previously completed reviews,
including mismatches introduced after their original successful finalization. These digests provide SQLite evidence consistency,
**not** a cryptographic signature against an attacker who can rewrite the
database and its fingerprints together.

### Concurrent specialist evidence integrity

The Go-verified path now uses the same bounded two-slot scheduling limit as
the persisted dependency graph; the native supervisor, not Go, owns the
actual passive scanner execution and SQLite writes. Both results are joined
before moving to the next batch. A denied role prevents that batch's tools
from starting; a cancelled or failed batch cannot be replayed automatically.
Each short-lived file-backed worker opens only the already migrated SQLite
database; it does not create a new database, re-run schema initialization or
change journal mode. This removes avoidable schema setup contention while
two registered passive analyzers start.
The native supervisor now claims the delegated role, specialist step and action
receipt in **one SQLite write transaction**, checking the exact registered role,
approved parent and completed dependencies. After work has joined, it commits
the delegation result, step result and SHA-256 action digest in **one
transaction**. A failed claim or stale delegation rolls back all three state
changes. Existing read-only scanners still run only under the prior approval,
and no finished specialist is automatically retried.

For a joined batch where just one passive specialist fails, the supervisor
persists **both** terminal specialist receipts and their result digests in
approved position order. The successful sibling's evidence is retained, while
the failure stops all further dependent batches and prohibits downstream
handoffs originating after the first failed result. Both failure orders are
covered by file-backed SQLite regression tests.
Once both action receipts have been claimed, Rust checks cancellation again
before launching workers. The SQLite action receipt also requires an uncancelled
running parent **when committing results**: a worker returning after cancellation
cannot silently overwrite the receipt with accepted evidence. On restart,
both in-flight specialists and their receipts are retired without replay,
while previously committed evidence remains intact. File-backed tests reopen
SQLite and verify terminal receipts, approved role order and handoff fingerprints.

### Crash recovery for claimed queues

When the queue has claimed a review but the Rust supervisor cannot start,
its terminal `interrupted` receipt also retires the parent approval in the
**same SQLite transaction**. Unfinished specialist steps, action receipts,
and delegated tasks are explicitly closed without executing any analyzers.
On desktop startup, recovery also reconciles older `interrupted` receipts
that still have an `approved` parent. Direct review execution refuses both
waiting and interrupted queue entries, even before reconciliation. Completed
evidence is preserved; waiting flows are never started automatically. Users
must create and approve a fresh review for any interrupted work.


## Isolated worker restart and claim safety

An isolated offline worker is a separately consented user action. The SQLite
worker audit ledger now allows only **one running receipt per approved review**.
An active worker prevents direct native review execution and FIFO queue
enrollment for that same review; a waiting/claimed queue also blocks starting a
worker. These authorization checks are performed in the same SQLite write
statement as the relevant claim, not as an earlier UI-only check.

On desktop startup, a still-running worker audit is retired as
`interrupted`, and its outstanding parent approval and unfinished specialist
tasks are closed in one SQLite transaction. Completed evidence is retained;
the stale review cannot be run or reused for a new worker. An operator must
approve a fresh review.

**Important:** a killed Docker CLI is not proof that its daemon-side container
was removed. The audit records the fixed
`application_restarted_cleanup_unconfirmed` code. Any such receipt, including
a failed worker with an unconfirmed cleanup, now **blocks all new isolated
worker claims across projects**, not only the original review. The Agents page
shows the saved cleanup hold count. An operator must explicitly request a
bounded, read-only Docker verification: `docker ps --all --filter
name=^/codetwin-scan- --format {{.Names}}` using the configured trusted CLI.
Only a successful empty container listing for the current configured daemon
allows SQLite to replace the outstanding codes with traceable
`*_cleanup_checked` codes. A failed command, timeout or any matching container
keeps the block. Operators must also ensure Docker is pointed at the correct
daemon/context; checking a different daemon does not prove earlier cleanup.
Restart recovery does **not** auto-run a scanner, auto-retry or delete containers.

## Adaptive follow-up after failure or interruption

After a fully approved automated review fails, the Go sidecar automatically
proposes a **new, unapproved** follow-up only for unfinished passive specialists
from the original reviewed scope. If source validation failed, the suggestion
contains only the mandatory recon and source prerequisite roles. If source
completed, the suggestion retains the registered optional roles that did not
finish. Completed optional specialists are excluded.

Go receives only specialist identifiers and terminal status codes. It receives
no raw source, credentials, scanner output, target addresses or report content.
Rust checks that the proposed roles are a **subset of the earlier reviewed
roles**, verifies the complete dependency DAG and persists a single immutable
follow-up draft in SQLite migration 0045. No draft is executed automatically;
the user must inspect the suggestion, create a new review and approve it again.
If a process stops before suggesting, **Suggest scoped follow-up** can generate
the same draft after restarting. Completed flows do not produce unnecessary
follow-up work. This is deterministic evidence/status-based adaptation—not an
LLM-generated action planner or unrestricted PentAGI autonomy.

## Protocol and security boundaries

- Rust sends one versioned JSON request on stdin, containing only the
  user-authored objective and at most twelve project-scoped role/status pairs
  from terminal review memory. Go sends one JSON `TaskProposal` on stdout.
  Neither raw source nor findings, run IDs, file paths or credentials are shared.
- There is no shell interpolation or HTTP port, no command execution, and no
  autonomous vulnerability exploitation in this Go module.
- A two-second sidecar handshake, ten-second planning deadline, 6000-byte response cap, strict JSON input,
  six-role allowlist and Rust DAG validation reject unexpected output.
- Go uses failed prior specialist outcomes to suggest bounded follow-up roles
  when appropriate. Every memory item must have a registered role and a
  terminal completed/failed status; unknown fields and oversized history fail
  closed. A memory suggestion never authorizes execution.
- `--refine` accepts a bounded, unapproved task proposal and a strictly
  typed add/remove/modify delta. Its two-pass delta algorithm is adapted
  from PentAGI's MIT-licensed `backend/pkg/providers/subtask_patch.go`.
  The original MIT license and provenance are retained under
  `services/security-engine/licenses/pentagi/`. The Go code is independent
  of PentAGI's PostgreSQL and provider runtime. Only registered optional
  passive specialists may be added, removed, or modified; the audited role
  order and mandatory task dependencies remain immutable. The desktop UI
  can refine a proposed plan before creating a review. Rust independently
  validates both the input and output task DAG, and the result is **not**
  executed or stored as an approved review until the user explicitly
  creates and approves it.
- Go also provides a read-only `--dispatch` protocol that consumes an existing
  persisted SQLite specialist DAG and lifecycle state from Rust. It computes
  dependency-ready tasks with a maximum of two concurrent slots. Invalid,
  cyclic, unregistered, failed or cancelled task states fail closed. The Rust
  desktop independently checks the ready set against its SQLite graph before
  showing it; no Go suggestion can approve, execute or expand a tool budget.
- For an **already approved** passive review, **Run with Go scheduling checks**
  invokes the Go scheduler before each registered Rust specialist. Go can deny
  the next role; it never executes the scanner, touches the SQLite database or
  alters the approved DAG. Rust persists each state transition and verifies all
  handoffs. After mandatory reconnaissance and source review, Rust requests Go
  scheduling approval for **each member** of a dependency-ready optional batch.
  When two independent roles occupy consecutive approved positions and the
  review uses file-backed SQLite, both durable running receipts are claimed
  before the native passive analyzers execute concurrently. The supervisor
  joins both threads, checks cancellation/deadlines, commits evidence in role
  order, and creates verifiable signed handoffs. Dependent or nonconsecutive
  roles fall back to serial execution; no speculative analyzer runs without its
  own successful Go scheduling decision. This is not arbitrary PentAGI tool
  execution. Rust persists each Go-gated allowed/denied decision in
  `go_dispatch_audit` (SQLite), including run, role, bounded ready roles,
  reason and time. The Agents page can display that audit. No source
  bytes, credentials or scanner output are saved in decision records.
- Go chooses registered passive specialists; Rust checks the indexed project,
  hashes, user approval, budgets, dependencies, cancellation and audit state.
- An unconfigured or unavailable binary is reported explicitly, not silently
  simulated. Go receives no credentials, project paths, source code, raw
  findings or stored report content.
- The same existing SQLite `native_agent_*` tables store approved reviews;
  no alternate database is created.
- Each approved passive specialist dispatch creates a `native_action_log`
  receipt in SQLite. Rust atomically claims the pending step and records its
  running receipt before ordinary sequential execution. For optional analyzers
  speculatively prefetched by the existing Rust parallel executor, the receipt
  instead tracks the supervisor's ordered **acceptance/commit** boundary, not
  the worker's earlier start time; the concurrent worker produces no durable
  handoff until Rust verifies and commits it. Finishing commits the step result
  and a SHA-256-only receipt together. The action log stores role, timestamps,
  terminal status and result digest, not raw source or scan output. Crash
  recovery marks any unfinished action as `interrupted` without replay, and
  desktop Agents can display the receipts. Go never writes this table.
- On restart after an interrupted active review, Rust atomically changes the
  running specialist to `interrupted`, queued specialist steps to `cancelled`,
  and unfinished delegated tasks to `cancelled`. Completed evidence and Go
  scheduling audit records remain intact. The parent review becomes
  `interrupted` with its cancellation flag set. Neither Go nor Rust will
  automatically resume any of those tasks: a new review and approval are
  required. Recovery can safely run more than once.
- Normal review failure or cancellation also finalizes the native steps and
  unfinished delegation records **within one SQLite transaction**. Cancelling
  a planned/approved review retires its queued specialists immediately;
  cancelling a running review sets its cancellation flag and the supervisor
  finalizes those statuses. The Go-gated path checks cancellation again
  **after** Go verification and **before** starting a native specialist, so
  approval checks cannot inadvertently cross a cancellation boundary.

## Upstream and scope

PentAGI's Flow/Task/Subtask/Agent separation informed this adapter's design.
**The original PentAGI orchestrator, exploit-tool packages, and
PostgreSQL-based services have not been copied into this module.**
The task-delta refinement logic is a separately licensed upstream-derived
component, not a wholesale PentAGI backend transplant. They cannot
be dropped unchanged into an SQLite-only desktop application. Reusing upstream
source directly will require a separately reviewed SQLite storage adapter,
dependency-license inventory, tool sandboxing, engagement authorization,
recovery tests, and a process-boundary contract. Do not present this
first bridge as full PentAGI parity.
