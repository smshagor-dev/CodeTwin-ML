# Local Git review

Projects → Git changes → Load Git changes reads the registered project's repository root. Refresh re-reads the current working tree; the displayed patch is a review snapshot, not an approval token for a later commit.

The first Git workflow increment exposes branch/HEAD, changed paths, staged patches, working-tree patches, renamed paths and bounded untracked text previews. Empty repositories, detached HEAD, binary files, missing Git, conflicts and inaccessible repositories have explicit states. A nested indexed project must be registered at its repository root before Git review; parent repository changes are not silently substituted.

Native commands resolve the root from the project ID in SQLite, release the database lock and run on a blocking worker. Review commands perform no mutations. Separate explicit actions create branches and selected staged commits. Local review/branch/commit actions perform no network or real-index writes. The separate explicit GitHub publication actions perform authenticated REST requests; staging remains external. Commit preparation can write unreachable tree objects; only the explicit commit action advances a branch reference. Global/system configuration and inherited repository overrides are excluded. Git ownership checks stay enabled. Repository hooks (including reference-transaction), external diff, textconv, fsmonitor and configured clean/process filters are disabled; filtered repositories therefore show raw working-tree content rather than executing project-supplied transformations. Submodules show Gitlink pointer changes; nested working-tree dirtiness is deliberately excluded to avoid invoking helpers configured only in nested repositories. Paths use Git's NUL-delimited porcelain status and literal pathspecs.

Each Git command has a 15-second timeout and 2 MiB output limit; status is limited to 500 changed paths. Untracked previews are limited to 256 KiB and UTF-8 regular files. Symlink content is not previewed. Non-UTF-8 paths fail explicitly rather than displaying an ambiguous lossy path. Git configuration and filesystem contents may still change between reads; branch creation verifies the displayed HEAD again within the Git reference transaction.

Validation uses actual temporary Git repositories for index/HEAD preservation, staged vs working-tree patches, literal wildcard filenames, renames, unborn/detached branches, binary/oversized files and disabled external helpers. Production browser checks use fixture IPC for UI behavior, request cancellation, escaped content and responsive layout. They do not replace native desktop GUI validation.

## Reviewed branch creation (CS-03 first increment)

After loading changes, expand Create branch, enter a name, and explicitly select Create at reviewed HEAD. The native command resolves the registered project root rather than accepting a UI-supplied filesystem path. It validates the branch and full SHA-1/SHA-256 object ID, then uses `git update-ref --stdin` with `verify HEAD`, `create refs/heads/<name>`, `prepare`, and `commit`. Changed HEAD, existing branch names, lock conflicts and invalid names abort the transaction. There is no fallback that overwrites an existing ref.

Branch creation leaves the checked-out branch, index and working tree in place. Switch branches externally when ready. The command returns the created branch and commit as a receipt; it does not claim the filesystem cannot change afterward. Initialized named branches are supported; detached/unborn repositories require an external Git action first. ASCII branch names are limited to 120 characters and checked by Git. Every subprocess uses a private empty hooks directory, disables configured filters/fsmonitor, excludes inherited Git configuration injections and preserves Git ownership checks. A trusted installed Git executable and OS filesystem access are prerequisites; this is not a sandbox against concurrent malicious filesystem mutation.

Real Git tests cover preservation of staged/unstaged bytes, stale HEAD, name collisions/injection, concurrent creation and a failing reference-transaction hook that must never execute. Browser fixtures cover explicit execution, exact reviewed HEAD, receipt/error rendering and disabled invalid input. Windows native GUI validation remains pending. Reference transaction semantics: https://git-scm.com/docs/git-update-ref.

## Selected staged commits (CS-03 second increment)

Stage files externally, load Git changes, expand Commit selected staged files, select paths, and enter author name/email/message. Prepare selected commit review displays the exact staged patch, expanded rename paths, author, message and parent. Author-name and message edge whitespace is normalized in the displayed preview. Editing inputs invalidates the displayed preview. Commit reviewed staged snapshot is a separate explicit action. Unstaged edits are not included; paths are never selected automatically.

Preparation uses a private temporary index initialized from the reviewed HEAD, then substitutes only selected stage-zero entries (including rename originals and deletions). The real index is never rewritten. Apply recomputes the tree/patch and compares a SHA-256 digest bound to the repository, HEAD, branch, entire logical staged index, selected paths and author/message. The digest is a content checksum, not an authentication credential. Changed staging, identity, message, branch or HEAD requires a fresh review. Working-tree edits can continue without changing the reviewed staged snapshot.

Commit creation uses local `commit-tree --no-gpg-sign` with explicit author/committer values and a UTC timestamp. Entered authorship is not authenticated. Git advances the explicitly reviewed branch using an old-OID compare-and-swap, so concurrent commits cannot silently overwrite it. It does not retarget HEAD or rewrite the real index. Other Git clients can still change files, the index or checkout state around these checks; the app is not a filesystem sandbox or a multi-client transaction covering every file. Avoid simultaneous external Git operations during apply. If another client switches branches after the final check, the update still targets the reviewed branch.

Conflicts, merge/rebase/cherry-pick/revert state, detached/unborn HEAD, selected symlinks/gitlinks/directories, non-UTF-8/binary content and empty selections are rejected. Limit: 50 expanded paths, 256 KiB per old/new blob, 2 MiB total old/new content, 4096-byte message. Hooks, filters, fsmonitor, external diff/textconv and signing commands are suppressed. Lazy promisor fetching is disabled and all Git transport protocols are denied; missing objects fail locally. Replacement refs are ignored so evidence uses actual stored objects. A trusted Git installation and filesystem remain prerequisites.

Previews and UI receipts are transient. Git objects, the branch ref and Git reflog are the durable result; there is no SQLite commit-plan history or automatic retry/recovery. If the app closes or a command result is lost, refresh and inspect Git HEAD/reflog before attempting more work. A ref may have advanced before an error/timeout is observed; the app never rolls it back automatically. The 15-second limit applies to each Git subprocess, not the whole multi-command workflow.

Validation uses real repositories for selected/unrelated staging preservation, unstaged edits, exact parent/author/message, digest invalidation, replay rejection, literal paths, deletion/rename, copy-source staging preservation, helper suppression, missing promisor objects and concurrent commits. Production browser fixtures cover explicit prepare/apply, no automatic execution, digest propagation, edit invalidation, failure/receipt state, escaped patches and mobile/theme layout. These do not replace physical Windows native GUI validation.

## Authenticated publication and draft PR (CS-03 third increment)

Load Git changes after a commit, expand Publish commit and open draft PR, and enter the explicit owner/repository and GitHub token. Publish displayed commit sends the exact displayed HEAD to the same branch name remotely. Open draft PR is a separate action enabled after a verified publication receipt; the native command independently verifies the remote SHA, base and repository before creation/reuse. There is no automatic push or PR.

The token is transient Rust/React memory, never SQLite, preferences, vault, local/session storage, command arguments or environment variables. Clear GitHub token removes it from this panel; refresh/project switch clears component state, and PR success clears the field. This does not promise cryptographic memory zeroization. No credential helper or Git network subprocess is used. All production requests target HTTPS api.github.com; redirects are refused, errors omit response bodies/token values, responses are capped at 2 MiB, and requests have 20-second/10-second connection timeouts. A 120-second budget is checked before each request; the final request and local Git work can extend beyond that budget.

A token needs repository Contents write and Pull requests write; workflow-file changes may need Workflows write. GitHub authorization/branch protections remain authoritative. Public/read access alone is insufficient. Default branch publication is blocked. Destination is explicitly supplied rather than inferred from repository-configured remotes. This baseline supports one unsigned standard-header SHA-1 commit with one parent already present remotely, up to 50 changed regular UTF-8 paths, 256 KiB per file and 2 MiB total file content. SHA-256, root/merge/signed commits, binary/non-UTF-8 uploads and symlink/gitlink/directory changes, full history, forks and GitHub Enterprise endpoints are unsupported. Regular-file deletion is supported.

The native flow verifies current local branch/HEAD, repository push permission, remote parent/tree identity and destination ref. Remote blobs, tree and commit are reconstructed from local objects; every returned SHA must match the local SHA before any branch-ref request. A missing branch uses create-ref; an existing parent branch uses force=false. Local state and remote ref are checked again before updating; GitHub's ref API is not an atomic expected-SHA compare-and-swap, so external branch/default-branch changes can race these checks. A forward/diverged branch fails instead of being forced. No local refs, index or worktree are changed by publication.

The resulting remote ref is re-read before reporting success. Repeating an explicit publication that already has the exact commit returns a receipt without uploading/updating again. PR creation verifies exact head SHA/ref, base, same head/base repository, draft status and GitHub URL; an existing matching draft is reused. Publication and PR receipts are transient. Durable results are on GitHub; no local SQLite publication history is added. Upload failures may leave unreachable remote objects, and a network failure may occur after ref/PR creation. There is no automatic retry or rollback: inspect GitHub and explicitly retry; existing SHA/draft checks make supported retries idempotent. Closing the panel does not cancel an already-dispatched native action.

Validation uses an owned loopback HTTP fixture that reconstructs actual blobs, trees and commits using an independent Git object database. It tests exact SHA reproduction, publication/PR separation, repeat actions, auth error redaction, default-branch/divergence/hash guards, stale local evidence, unchanged local index/HEAD and foreign PR rejection. Production browser fixtures test credential fields, no automatic requests, disabled PR before publication, auth failure, separate PR action, token clearing and project scope reset. These are not live GitHub user-token or physical Windows native GUI validation; both remain pending. REST references: https://docs.github.com/en/rest/git/commits, https://docs.github.com/en/rest/git/refs, https://docs.github.com/en/rest/pulls/pulls.

CS-03 has a bounded implementation baseline. Next milestone: CS-04 finding comparison and redacted reports.
