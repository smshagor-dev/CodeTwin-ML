# Release gates

CodeTwin ML treats validation evidence as part of the product contract. A change is not considered release-ready merely because a pull request is mergeable.

## Required validation

Before a production release, the latest release candidate must have completed the repository CI jobs on real runners:

- `rust`
- `windows-qa`
- `python`
- `frontend`

A job with no allocated runner, no executed steps, or missing logs is an infrastructure failure and must not be interpreted as a pass.

## Reproducible dependency state

Release candidates should commit the package-manager lockfiles required for deterministic dependency resolution. Lockfiles must be generated by the real package manager from reachable registries or an approved trusted cache; placeholder or fabricated integrity metadata is not acceptable.

## Installer and dataset boundary

The base desktop application must remain installable without the optional OpenMindAI Dataset package. Dataset-backed features may only claim readiness after the release manifest and all referenced assets have been built from their pinned upstream revisions and their sizes and SHA-256 hashes have been verified.

## Desktop release workflow

The dedicated Windows release workflow is `.github/workflows/desktop-release.yml`. It is intentionally fail-closed:

- both `Cargo.lock` and `package-lock.json` must already exist and must have been generated by the real package managers from reachable registries or an approved trusted cache;
- the release tag must be `vMAJOR.MINOR.PATCH` and its version must match the root package, Cargo workspace, and Tauri manifests;
- publishing requires an existing tag that points to the exact workflow commit;
- the same Rust, Windows QA, Python, and frontend validation families must pass before packaging;
- Windows signing requires protected `WINDOWS_CERTIFICATE`, `WINDOWS_CERTIFICATE_PASSWORD`, and `WINDOWS_TIMESTAMP_URL` secrets;
- release builds use a runtime-only Tauri configuration overlay so certificate thumbprints and timestamp configuration are never committed;
- the generated NSIS installer and installed application executable must both have a valid Authenticode signature;
- the clean Windows runner performs a silent base install, verifies that optional dataset terms were not accepted and no dataset state was created, runs the installed `--release-smoke` database/index/dashboard-backend check, starts the GUI, and silently uninstalls it;
- release evidence includes SHA-256 checksums, Cargo metadata, the npm dependency inventory, and a build provenance JSON document;
- repositories that support GitHub artifact attestations may set the repository variable `ENABLE_GITHUB_ATTESTATION=true`; the workflow does not require that feature on plans where private-repository attestations are unavailable;
- release publication refuses to overwrite an existing GitHub Release.

The internal `--release-smoke <fixture-repository> <sqlite-path>` mode does not start the Tauri UI. It creates/opens SQLite, indexes the supplied local fixture, executes the graph query used by the dashboard, and verifies the workspace summary exposes the indexed project. It is intended for installed-artifact validation, not as a user-facing application mode.

Silent NSIS installs skip the optional OpenMindAI Dataset prompt and never implicitly accept its terms. Interactive installs retain the explicit Yes / Retry / Cancel dataset flow.

The presence of this workflow is not proof that a production release is validated. Until real lockfiles exist, GitHub Actions allocate real runners, signing secrets are configured, and the signed installer smoke actually passes, release readiness remains blocked.

## Repair validation

An applied repair is not a verified repair. Verification requires a fresh repository index and, when a deterministic finding is linked, the responsible analyzer must independently resolve that finding in the new state.

## QA execution boundary

The Windows QA backend may expose execution only when the runtime reports the complete strict capability floor: detached hash-bound project mirror, approved copied runtime/toolchain surface, zero-capability LPAC identity, Job Object/process limits, bounded handles/output, and the required network/desktop isolation checks. Unsupported platforms remain planning-only and there is no weaker fallback.

Implementation availability is not release validation. A production release that claims Windows QA execution must still run the `windows-qa` job on a real allocated Windows runner and preserve the resulting logs/evidence; `runner_id=0` or zero executed steps is an infrastructure failure, not a pass.

## Merge discipline

When stacked pull requests are unavoidable, parent changes must reach `main` before a child is rebased or merged into `main`. A child pull request reporting `merged` on a feature-branch base does not prove that its changes reached the default branch; verify the resulting `main` tree directly.
