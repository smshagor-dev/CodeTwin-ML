# Release gates

CodeTwin ML treats validation evidence as part of the product contract. A change is not considered release-ready merely because a pull request is mergeable.

## Required validation

Before a production release, the latest release candidate must have completed the repository CI jobs on real runners:

- `rust`
- `windows-qa`
- `python`
- `frontend`

A job with no allocated runner, no executed steps, or missing logs is an infrastructure failure and must not be interpreted as a pass.

## Reproducible dependency state

Release candidates should commit the package-manager lockfiles required for deterministic dependency resolution. Lockfiles must be generated by the real package manager from reachable registries or an approved trusted cache; placeholder or fabricated integrity metadata is not acceptable.

## Installer and dataset boundary

The base desktop application must remain installable without the optional OpenMindAI Dataset package. Dataset-backed features may only claim readiness after the release manifest and all referenced assets have been built from their pinned upstream revisions and their sizes and SHA-256 hashes have been verified.

## Repair validation

An applied repair is not a verified repair. Verification requires a fresh repository index and, when a deterministic finding is linked, the responsible analyzer must independently resolve that finding in the new state.

## QA execution boundary

QA execution remains disabled until its documented filesystem, network, desktop/window-station, runtime provenance, and adversarial Windows validation requirements are satisfied. Planning or containment scaffolding is not an execution result.

## Merge discipline

When stacked pull requests are unavoidable, parent changes must reach `main` before a child is rebased or merged into `main`. A child pull request reporting `merged` on a feature-branch base does not prove that its changes reached the default branch; verify the resulting `main` tree directly.
